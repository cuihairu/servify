01

执行摘要

四个结论先行。评级分布：15 个维度中 7 项完整、5 项部分、1 项骨架（接口在、通路未通）、2 项缺失。

完成度 · COMPLETENESS定位内完成度高，定位外普遍未启动

对照 V1 定位（Web 独立站智能客服），核心链路——AI 首答、人工接管、转人工队列、工单闭环、知识库——全部真实可用且质量扎实。缺口集中在定位之外：主动触达、坐席考核联动未启动，全渠道仅 Web/Email 真实通路。质检运营（规则+LLM 打分+抽检工作台）、坐席组亲和路由、远程协助录制标注已于 2026-09 落地。

7 完整 · 5 部分 · 1 骨架 · 2 缺失（共 15 维）

护城河 · MOATAI 编排与安全纵深达到商业产品水准

AI 侧：QueryOrchestrator 支持 LLM 工具循环（工单/客户查询、转人工）、输入校验与输出脱敏、prompt 审计、置信度评估与 dify→weknora→legacy 三级 fallback 加熔断——架构路线对齐 Intercom Fin 一类产品。安全侧：四层令牌吊销、会话风险评分、tenant/workspace 双级 scope 强制、配置审批工作流，治理深度超出同体量产品。

关键缺口 · GAPS三处「上线即撞墙」级的定位内缺口

① 文件存储仅有本地盘 Provider，多副本/容器化部署即失效，无 S3/OSS；② 管理端无 SSO/OIDC，企业管理员接入的标准诉求；③ 渠道矩阵中 Email 是成本最低的下一通路（SMTP 收发即可起步）。三者均在 V1 定位辐射范围内。

设计判定 · VERDICT架构合理且有守卫，风险在演进纪律

模块化 DDD 分层 + 静态边界检查 + Provider 中立化（能力矩阵/降级/熔断）是同类开源项目少见的工程水准。主要风险：数据迁移依赖 GORM AutoMigrate（非版本化，无法表达字段重命名与数据回填）；services/ 与 modules/ 双轨并存，AI 服务已积累三代实现，收敛计划缺位。

02

对标产品速览

选取国际 SaaS 双雄、最接近的开源对标、性价比 SaaS 与国内三强，覆盖 servify 可能进入的每个市场位置。

Chatwoot 开源 · 最接近对标

开源客服系统，全渠道广（7+ 渠道）、campaign 主动触达、开放 API/Webhook 完整；但 AI 能力（Captain）起步阶段，工单深度浅。与 servify 互为镜像：它广而浅，servify 窄而深。

Intercom SaaS 旗舰

Fin AI Agent 为行业标杆，Outbound 主动触达是核心商业化引擎，Messenger 生态开放平台最强。servify AI 编排的架构参照系。

Zendesk Suite 工单与生态王者

全渠道+工单领域事实标准，应用市场生态最大，QA 质检为收费模块；AI 能力额外计价。工单状态机与 SLA 体系的成熟度标尺。

Freshdesk 性价比 SaaS

Freddy AI + 内置呼叫中心（Freshcaller）+ 完整工单/自动化，中小市场渗透率高。「一套价格买齐全家」路线的代表。

智齿科技 国内一体化

全渠道+呼叫中心+工单+质检一体，微信生态深，人机结合质检是标配能力。国内交付形态与质检标准的参照。

Udesk 国内大型 B2B

大型企业客服平台，全渠道与呼叫中心成熟，开放集成能力中等。国内中大型客户的功能预期基线。

网易七鱼 国内 SaaS

电商场景深，机器人会话占比高，质检与坐席管理成熟。AI 机器人商业落地的国内样本。

差距分析：按定位分级

不是所有差距都需要补。按「是否落在 V1 定位（Web 优先 · AI 首答 · 人工接管 · 工单闭环 · 独立部署）辐射范围内」分为两档。

IN-SCOPE · 定位内必补上线即撞墙 / 核心承诺打折

  • 对象存储 Provider P0　storage 抽象只有 LocalProvider（./uploads + 静态路由）。独立部署定位恰恰意味着容器化/多副本是常态，本地盘存储在此形态下必然损坏。S3 协议实现即可同时覆盖 AWS/MinIO/OSS。
  • OIDC SSO 管理端登录 P0　认证只有自建注册/登录/刷新。企业独立部署场景下，接入客户 IdP（OIDC/LDAP）是安全问卷必过项，也是安全维度「完整」评级的最后一公里。
  • 版本化数据迁移 P0　当前依赖 GORM AutoMigrate（详见设计评审）。字段重命名、数据回填、回滚均无法表达，升级路径不可审计。
  • Email 渠道 P1　channel 契约已就绪，IMAP/SMTP 适配器即可落地「Web 优先」之外的第一条真实通路；AI 首答管线无需改动即可复用。 已落地 dde9c1f
  • SSO 之外的认证补强 P1　TOTP 双因素；当前会话风险评分体系已具备风控底座，补强成本低。
  • AI 效果回归 P1　golden set + 置信度阈值 CI 回归。「AI 首答」是产品第一承诺，需要可度量的质量线。

OUT-OF-SCOPE · 定位外缓做按市场反馈决定，不背竞品全家桶包袱

  • 主动触达 / Campaign 缓　Intercom 的第二引擎、国内三强的商业化核心，但与 servify「服务台」定位正交。eventbus + 现有渠道随时可起步，不必现在做。
  • 呼叫中心真实通路 缓　voiceprotocol 架构已建，建议只验证不扩张：接一条托管 PSTN 通路证明设计成立即可，h323/FreeSWITCH 枚举可长期保持 reserved。
  • 质检运营 看市场　国内市场交付几乎必问；国际市场可后置。规则质检成本低，LLM 打分可复用 AI 编排。 已落地 847e14f / 7a40b0a / 302bb31
  • 移动端 SDK 缓　react/vue/vanilla 三绑定覆盖 Web；RN 绑定等有客户诉求再做，contracts 能力协商机制已为其预留。
  • 开放平台闭环 P1–P2　出站 Webhook + API Key 是最小闭环，做齐即可宣称「可集成」，不必追 Zendesk 市场规模。 已落地 9aef039 / e1967cf / d004a15

设计合理性评审

以下判断基于全量代码走读（12 模块 / 16 平台组件 / 路由与装配层）与一次深度评审会话中实际定位并修复的四个并发/一致性缺陷。

WHAT WORKS · 做对的六件事同类开源少见的水准

1 · 架构有守卫，不只靠约定

模块化 DDD（delivery/contract/application/domain/infra）之外，make module-boundaries 用 19KB 静态规则持续校验模块依赖方向——多数项目分层只活在文档里，这里活在 CI 里。

2 · Provider 中立化是系统性的

LLM、Embedding、知识检索、语音录音/转写、事件总线、存储六个面全部接口化，且带能力声明矩阵、fallback 优先级与熔断策略（platform/aiprovider/matrix.go）。供应商锁定风险被一次性、结构性地解除。

3 · 配置治理达到商业产品水准

runtime→tenant→workspace 三级配置解析 + 变更 diff/风险分级/审批/回滚工作流，同类解析器复用于 Portal/OpenAI/Dify/WeKnora/SessionRisk 五处。多数商业产品也只有「改了就生效」。

4 · 安全纵深成体系而非散点

四层令牌吊销（jti/用户版本/会话级/批量）+ 会话风险评分 + 生产环境不安全默认拒绝启动 + check-security-baseline 路由安全面自检。安全是跨层设计，不是中间件补丁。

5 · 事件驱动用在了对的地方

eventbus 双后端（inmemory / Redis Streams + consumer group），analytics 增量统计与 automation 触发都挂在事件上。读模型与写路径解耦，为后续自定义报表铺了路。

6 · 工程配套完整度罕见

8-job CI、race 测试三层 tier、核心包覆盖率 98%+、dify/weknora/knowledge/auth-session 验收测试、OTel+Prometheus+Grafana 面板+runbook+告警规则。测试基建近年真实扛住了四次产品级缺陷的回归。

FAILURE PATTERNS · 四个真实缺陷归纳的模式均为评审会话中定位并修复

并发边界 · WS 读锁下写共享 map

WebSocketHub 在读锁保护下修改共享状态，race detector 才暴露。模式：手写并发容器的锁粒度靠直觉而非契约。所有共享 map 应集中收口并强制过 race tier。

流式协议完整性 · OpenAI 流式丢 tool call

流式聚合路径丢失 tool call 增量片段，非流式路径无此问题。模式：流式与非流式是两条代码路径，只有一条被认真测试。流式解析需要独立的合同测试。

分布式时序 · Redis 订阅确认窗口丢事件

pubsub Receive() 确认前其他实例发布的状态变更永久丢失，多实例下坐席在线视图静默不一致。模式：典型的「订阅建立≠开始接收」陷阱；修复为订阅确认 + 启动全量兜底同步。此类问题单实例测试永远发现不了。

测试隔离 · 命名内存库撞库 + 全局计数器泄漏

固定名 SQLite 内存库在 -count 重跑时命中同一库；进程级限流计数器跨测试累积。模式：测试资源生命周期未被当作接口设计。已全仓 50 处统一为唯一 DSN + 显式 Reset。

共同根源

四个缺陷都不是设计错误，而是「快路径正确、边界路径未被系统检验」——并发边界、协议增量、分布式时序、测试隔离恰好是四类最容易被单实例、单次执行的测试掩盖的路径。race tier 与验收测试的存在是对的，建议把「多实例行为」纳入验收测试的常设维度。

部署核对 · SERVIFY_JWT_SECRET——config.yml 默认值 ${SERVIFY_JWT_SECRET} 在环境变量未设置时展开为空串。此时密码登录与 SSO 均能正常完成并签发会话，但所有 Bearer 鉴权接口会被中间件的空 secret 防护整体拒绝（401 invalid token or server misconfig）。SSO 端到端联调（Keycloak 容器）实测发现；独立部署核对单必须包含「显式设置 SERVIFY_JWT_SECRET」一项。

评级方法

评级口径——完整：该维度核心场景真实可用且有测试覆盖；部分：有真实实现但覆盖不全或表达力不足；骨架：架构/契约/实体已建但无真实通路（区别于「缺失」，因为它代表已投入的设计资产）；缺失：基本无实现。

竞品点阵口径——依据各产品公开文档与定价页的功能现状（2026-09），●=成熟/标配，◐=部分具备或需高级版本，○=弱或缺失。付费墙内能力按「可用性」而非「免费性」计。

证据边界——Servify 侧结论全部来自代码走读（基准 commit 0686dd3）；竞品侧来自公开资料，未做产品实测。评分为主观定标，用于横向比较而非绝对度量。
