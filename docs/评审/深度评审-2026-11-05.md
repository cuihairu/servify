# Servify 深度评审（2026-11-05）

## 范围、结论与证据口径

本评审按当前工作树静态抽查，竞品以 2026-11-05 可访问的官方资料为准；产品价格及套餐可能变化。代码存在不等于真实环境验收通过；本文未运行外部服务、完整测试或基准测试，也未审完所有入口。以下“未证实”不等于断言功能不存在。

**结论：定位可成立，但尚未证明可以可靠交付。** 它是企业自行部署的 Web 优先智能客服，而非通用多渠道平台；首版链路为嵌入、知识首答、人工、转接、工单（`README.zh.md:17-25`，`README.md:29-68`，`docs/zh/v1-product-scope.md:66-124`）。仓库声明已有会话、路由、工单、知识索引、答案反馈和 Web SDK；原生 SDK 已有实现但语音和多渠道不属于首版中心（`README.zh.md:29-42`）。真实外部知识服务的三家验收仍缺资源（`todo.md:7`，`docs/review/kb-real-acceptance-resources-2026-10-30.md:3-17`）。最高优先级是无依据回答、写入一致性、转接一致性和真实服务证据，而不是新增平台功能。

## 二、依赖与验收链路

根模块主要是文档生成 `swag` 和 YAML（`go.mod:1-9`），实际服务依赖看嵌套模块 `apps/server/go.mod:1-44`：Gin HTTP；GORM + PostgreSQL/SQLite，migrate 迁移；pgvector-go 向量；Gorilla WebSocket、Pion WebRTC；Redis 客户端；OIDC、OAuth2、OTP、x/crypto；AWS S3；IMAP（beta）；Prometheus、OpenTelemetry、logrus、lumberjack；Viper/mapstructure/YAML 配置、Cobra CLI、UUID、Excelize；miniredis/testify 测试。`gin-contrib/sse` 为间接依赖（`apps/server/go.mod` 的间接依赖段），SSE 可用标准 HTTP；未列专用 LLM SDK、embedding SDK 或独立任务队列框架，不意味着未实现：自有 `internal/platform/llm`、`internal/platform/embedding` 和 Redis Streams 事件实现承担这些职责（`apps/server/internal/platform/eventbus/redis_bus.go:73-120`）。建议保持自有业务接口，协议复杂度增加时评估成熟 SDK；不要仅为依赖数量引入框架。

| 链路 | 依赖与判断 |
| --- | --- |
| Web → 会话 | Gin/WS 和 SDK 已具备基础（`README.zh.md:40-41`）；生产仍需真实浏览器断线、恢复、鉴权和部署验收，库本身不保证语义。 |
| RAG → AI | pgvector、embedding 抽象与外部 provider 足够做 V1，非必须自研向量数据库；Postgres migration 安装扩展和 IVFFlat（`apps/server/internal/app/bootstrap/migrations/000001_init.up.sql:25,199`），另一 chunks 表固定 1536 维（`000025_knowledge_bases_chunks.up.sql:41`），需验证实际查询表、模型维度和索引计划，不能据此宣称所有查询已加速。本地 provider 先取最新候选后排序，且 hybrid 映射 cosine（`apps/server/internal/platform/knowledgeprovider/local/provider.go:94-120,129-145,292-298`），适合小规模和降级，不是真正混合检索。 |
| 流式 | Gorilla 适合双向实时会话；单向 AI token 可用 SSE，现有流式无需为换协议而重写；重点验证取消、断线、部分输出与落库一致性（`apps/server/internal/modules/ai/delivery/enhanced_service.go:298-314`；`todo.md` 已完成 AI 首答流式条目）。 |
| 人工/转接 | 路由、等待和转派有代码；可靠性取决于状态原子性、目标有效性和事件恢复，而不是新增库（`apps/server/internal/modules/conversation/application/service.go:230-268`；`todo.md:12`）。 |
| 工单 | ORM 足以实现状态机、事务和审计；当前创建跨多次调用、终态不可重开，需明确规则与修复（`apps/server/internal/modules/ticket/application/command_service.go:32-86`，`status_policy.go:11-35`）。 |

可用开源组件补齐的候选：文档解析/抽取和网页抓取、成熟 LLM SDK 的协议与流式解析、PostgreSQL 全文检索/pgvector 或外部 RAG 平台、持久任务队列与重试库、OpenTelemetry 收集器。均需做许可证、隔离、版本、运维成本及契约评估，不能声称装库即可完成业务。需要自行设计且工作量较大：跨会话/队列/坐席的并发一致性和权限；工单状态与审计、通知和幂等；业务知识集/人工标注评测、拒答和校准；知识源生命周期及租户映射；实际部署恢复、故障演练与数据治理。这些由首版范围和当前实现共同决定（`docs/zh/v1-product-scope.md:78-124`；下节代码证据）。

## 三、架构与代码抽查

**模块边界：部分名副其实。** 这是 `apps/server` 下一个 Go 模块与单体进程内的包分层，而非 `application.test/apps/bin` 三个独立运行模块；README 实际列 `apps/server`、admin、demo 等（`README.zh.md:72-85`），架构列 27 个一级模块、7 个核心、其余为子能力（`ARCHITECTURE.md:58-62`）。现状文档称 14 个完整分层、13 个薄壳（`docs/zh/current-architecture.md:9-17,55-105`），与 README “每个模块具备四层”绝对表述（`README.zh.md:124-127`）矛盾。`internal/models` 仍被 AI application 引用（`apps/server/internal/modules/ai/application/handoff_policy.go:3-6`），实际依赖并非完全独立领域模型；现有边界脚本是守卫关键边界，不等于隔离所有耦合（`docs/zh/current-architecture.md:99-105`）。建议修正文案、以业务聚合和依赖规则衡量，不按目录数追求纯净分层。

1. **会话创建：** application 校验 ID，保存后记录默认租户指标并发布事件（`apps/server/internal/modules/conversation/application/service.go:51-72`）。指标固定 `default` 是明确的归因限制，不能用于租户级统计；写入与发布分离，应验证丢事件恢复，不据此断言所有生产入口都走这条路径。
2. **AI 首答：** 零命中允许 LLM 直接作答，置信度固定 0.6；低置信只附建议、不阻止答案或执行转接；无分数命中默认 0.85（`apps/server/internal/modules/ai/delivery/enhanced_service.go:323-358,510-521`）。这与“不确定澄清、不编造”目标存在缺口（`docs/zh/v1-product-scope.md:78-86`）；检索分数或常数不能视为经校准的正确率。转人工关键词使用子串，历史超过 5 条即触发（`apps/server/internal/modules/ai/application/handoff_policy.go:9-33`），例如英文 agent 可误命中包含该子串的普通词；应以真实语料评估误报漏报和不同入口调用情况。
3. **转接：** `Transfer` 在此方法中未验证目标坐席是否可接、未见版本比较，读取后整体更新，并忽略系统消息写入错误（`apps/server/internal/modules/conversation/application/service.go:230-261`）；并发覆盖、无效目标和缺失时间线是该路径的风险，外层可能有校验，须用真实入口复现。不要把单方法观察扩大为全系统漏洞。
4. **工单：** 创建先写工单，再写状态记录，再发布事件；后两步失败会返回错误但前一步可能已提交，重试可能产生重复（`apps/server/internal/modules/ticket/application/command_service.go:76-85`）。分配方法有可用性检查和专门 repository（同文件 `:162-195`），但创建一致性仍需事务/outbox。状态策略不允许 resolved/closed 回 open（`status_policy.go:16-35`）；客户追问的重开或新单规则需产品决定，不应直接宣称实现缺陷。
5. **知识检索：** 本地检索按 ID 倒序截断候选再计算余弦，旧但相关的内容可能被漏掉；`hybrid` 实际等同 cosine，分数又做立方根变换（`apps/server/internal/platform/knowledgeprovider/local/provider.go:111-145,282-298`）。这不是 BM25+向量融合，阈值不能直接跨 provider 比较；需用可复现数据集测召回和延迟。

## 四、WeKnora 声明对照

存档标题称完成，正文已明确混合检索由 WeKnora 服务实现、Servify 透传策略（`WEKNORA_IMPLEMENTATION_COMPLETE.md:1-8,19-24`）；provider 确实实现 Search、文本上传、删除、健康检查（`apps/server/internal/platform/knowledgeprovider/weknora/provider.go:25-55,61-100,110-114`）。但 `RebuildIndex` 非空 client 即返回 nil，未调用外部重建（同文件 `:103-108`）：若调用者视成功为已重建，会误报。更新采用先删旧后上传，上传失败会留下远端旧文档已删除的窗口（`:69-85`）；删除使用配置的 `knowledgeID`，而搜索/上传可按请求解析 namespace（`:29-35,65,90-100`），多知识库删除应验证路由是否正确。

历史 Docker 报告明确使用 WeKnora **Mock**，上传与同步仅部分通过（`docs/acceptance-weknora-docker.md:3-5,22-27`）；真实端点、版本和凭证仍待提供（`docs/review/kb-real-acceptance-resources-2026-10-30.md:5-17`）。因此结论是“适配代码和模拟协议已实现，真实兼容及效果未完成验收”，不是完成真实生产集成。存档中的 60%/85% 和无限扩展没有给出数据集/实验方法（`WEKNORA_IMPLEMENTATION_COMPLETE.md:85-95`），不能当质量证据；同文件 `:73-76` 初始化命令也需核实是否仍存在。`config.weknora.yml:40-54` 默认启 Dify、关 WeKnora，且 RAGFlow 关闭（`:73-79`），直接使用该模板不能证明命中 WeKnora；模板还含示例密钥、JWT 和宽泛 CORS（`:55-57,106-108,147-153`），应以生产校验为准，不能当安全生产配置。

## 五、执行次序与验收

先处理 P0 的无依据首答、创建一致性、转接和 WeKnora 假成功；然后取得隔离的真实服务和凭据跑三家验收，逐家记录版本、数据和失败证据（现有资源清单 `docs/review/kb-real-acceptance-resources-2026-10-30.md:19-27`）。P1 测量检索和业务质量、补齐重开策略和可观察性；P2 再根据客户需求做渠道、门户和远程协助。逐项可验收任务见根目录 `todo.md` 的同日章节。所有竞品机会是产品假设，需客户访谈和真实部署数据验证。
