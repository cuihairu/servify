# Servify Acceptance Checklist

This checklist exists to prevent misjudging "there is an entry point in the code" as "the feature is deliverable"; it is not for proving "it looks about done".

At acceptance time, every function item must have all 4 evidence types below, otherwise it never counts as done:

1. Code entry: a route, command, or call entry clearly exists.
2. Automated tests: at least relevant unit tests, integration tests, or command-level verification.
3. Runtime evidence: the service actually starts, the interface is accessible, and requests and responses behave as expected.
4. Data evidence: where the database, state transitions, files, or external dependencies are involved, before/after state changes are visible.

## Status Definitions

- `unverified`: only confirmed that a code entry exists; not actually run through.
- `partially passed`: compile or unit tests pass, but key business chains, exception paths, or data persistence are unverified.
- `passed`: has all four evidence types — code, tests, runtime, data.
- `blocked`: missing config, dependency, permission, environment, or data; cannot be verified for now.

## How to Use

First prepare the runtime environment:

```bash
make migrate DB_HOST=localhost DB_PORT=5432 DB_USER=postgres DB_PASSWORD=password DB_NAME=servify
make run-cli CONFIG=./config.yml
make run-knowledge-provider CONFIG=./config.weknora.yml
make run-weknora CONFIG=./config.weknora.yml
# `run-knowledge-provider` 是通用 alias；两者都仅用于 WeKnora compatibility / mock 验收
# 默认知识库 provider 仍以 Dify 为主
```

Common baseline validation commands:

```bash
make build
make build-knowledge-provider
make build-weknora
make test
go test -tags weknora ./apps/server/cmd ./apps/server/internal/handlers ./apps/server/pkg/weknora/...
```

Each entry is recorded with the template below:

| Field | Content |
| --- | --- |
| Function item | e.g. "Create ticket" |
| Entry | route / CLI / page |
| Preconditions | database, config, auth, dependent services |
| Steps | precise down to request parameters or actions |
| Expected result | status code, response body, state change |
| Automated evidence | related test files or commands |
| Manual evidence | curl results, screenshots, logs, DB query results |
| Status | unverified / partially passed / passed / blocked |

## Veto Items

If any of the following fails, "completed" may not be claimed externally:

- The service cannot start.
- Database migration fails.
- Core routes return 500 or a response structure that does not match the contract.
- After create the item cannot be queried, or after update the state does not change.
- Auth and permission middleware fail.
- When the external knowledge provider is unavailable there is no fallback or the error is uncontrollable.
- Key flows have only the happy path, with no exception-path verification.

## Permission and Exception Paths Must Be Additionally Verified

Even if the main flow passes, completion cannot be declared directly; the following must also be covered:

- Whether unauthenticated access to `/api/*` is correctly intercepted.
- Whether insufficient-permission access to different resources returns correct errors.
- Whether illegal parameters return `400` instead of `500`.
- Whether querying a nonexistent ID returns `404` or an explicit error.
- Whether external dependency failures produce degradation, retry, or circuit breaker behavior.
- Whether duplicate submissions, concurrent operations, idempotency, etc. behave as expected.

The relevant entries are in the auth and resource permission middleware registrations in [router.go](../apps/server/internal/app/server/router.go).

## Suggested Acceptance Execution Order

1. Environment tier: `make migrate`, `make build`, `make build-knowledge-provider`, service startup.
2. Liveness tier: `/health`, `/ready`, metrics.
3. Core business tier: customers, agents, tickets, session transfer.
4. Value-added tier: AI, knowledge base, automation, statistics, SLA.
5. Extended tier: voice, public survey, public knowledge base.
6. Negative and permission tier: unauthorized, illegal parameters, external dependency failures.

## Minimum Bar for Claiming "Completed" Externally

At least the following must hold before saying "this module passed acceptance":

- Core routes' happy path and exception paths both run through.
- Automated tests cover the module's main read/write paths.
- Data persistence, state transitions, exports, or side effects have been actually verified.
- The corresponding entries are marked `passed` item by item in this checklist, with evidence attached.

Otherwise, the most that can be said is:

- "The code entry exists"
- "The build passes"
- "Some tests pass"
- "The feature is still pending integration/acceptance"
