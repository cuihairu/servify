## 1. 聊天平台：先完成一个授权测试群的真实闭环

**推荐决策：保持 Telegram 长轮询试点；暂停扩展平台和功能，优先补齐 Phase 0 的真实凭据、逐群授权与验证记录。**

最新事实：todo.md:7 的 10 月 30 日记录显示，公告 HTTP 面已由用户明确授权并实现（`ae18f1f`），停用安装的出站门禁与逐会话入站授权门也已补齐（`d8a8d99`）。当前不能再将“是否建 notify”当成待决策。剩余是外部真实 token 与 Phase 0 证据，不是缺另一层适配器代码。

理由：

1. **成本：**已有适配器、管理 API、重放和离线测试，复用它们比重做平台接入省事；主要新增成本是管理员协调与一次真实验证。
2. **收益：**真实验证能证明实际可见消息范围、凭据有效性及端到端连接；离线模拟只能证明预设条件下代码成立。
3. **风险：**拿到 token 不等于取得群消息读取授权。专用 bot 只加入获批测试群，可减少误收无关群消息的机会。
4. **边界：**10 月 30 日实现会把未授权会话的事件隔离，并可能保留原始负载；“不进入正常会话”不等于“完全没保存”。因此测试范围要从 bot 加群范围就控制住。
5. **决策思路：**先补最接近交付的证据缺口。如果首批客户明确不用 Telegram，再重新选平台；目前没有这样的新证据，换平台只会增加不确定性。

**立即执行动作（后续交办）：**

- 产品负责人先确定一个专用测试群、管理员及目标 Servify 租户/工作区；管理员通过受控运行环境注入 bot 凭据，不把明文放入报告或聊天。
- 在启动采集前，记录群同意、实际消息可见范围、群白名单、保存期限及数据驻留要求。原始负载若启用留存，配置本机加密与不超过 30 天的清理；规范化消息保存期限另行明确。
- 运维使用已有 installations/capabilities API 写入安装映射和真实观察到的能力，再 reload。能力快照是授权观察记录，不能为了启动而虚填。
- 用无敏感内容的测试消息核对：授权群进入会话、重投去重、无观察授权的测试会话进入隔离而不进入正常流、关闭安装后停止收发。公告面单独验证，不扩大入站授权范围。
- 留存脱敏结果、测试时间及负责人；完成后才能关闭真实联调阻塞。凭据未到时只保留一次明确的待提供清单，不重复跑无法成功的联调。

**明确不做／延后：**不新增 Slack/飞书等平台，不扩展附件、编辑删除等能力；不重建 notify 或 replay；不把已实现公告面解释为已获真实群采集许可。

解锁所需最小输入：凭据的运行时注入、测试群及管理员、租户/工作区归属、授权与留存记录。参考：`docs/zh/chat-platform-integration-contract.md`；`chat_connectors.go:325`、`telegram/adapter.go:354`、`chat_connector_handler.go:582`（均位于 `apps/server/internal/` 对应目录）。

## 4. 租户翻译配额：维持软保护口径

**推荐决策：认可已代决方案，保留 `limit + unit(requests|tokens) + window(hour|day|month)`、Redis 固定窗口、租户／工作区只覆盖 limit、默认关闭、计量故障放行；开启时逐场景验证，不把它当财务硬预算。**

来源：todo.md:22 的“已代决待核”；`docs/design/tenant-quota-policy.md` §3—4。代码 `apps/server/internal/modules/translation/delivery/quota_gate.go` 证实：tokens 在成功后记账、无租户时跳过计量、meter 故障放行、非空 tokens 批量请求因无 usage 合约而拒绝。

理由：

1. **成本：**复用 Redis 和既有治理写面，不引入持久计费账本；只覆盖额度数值比每租户切换计量方法简单。
2. **收益：**能抑制持续滥用，额度配置可按租户差异化，适合作为服务保护。
3. **风险：**tokens 是先调用后记账，例如剩余 10 个 token，单次用了 100 个，仍可能越限；并发、缺失 usage、计量故障也会扩大超额。
4. **取舍：**故障放行优先保证翻译可用，却不能保证费用绝不增加。业务若要求“费用不能超”，应走第 7 项，不能只改宣传或 limit 数值。

**立即执行动作（后续交办）：**

- 将当前方案作为默认有效口径，无新需求时不重新设计；暂不统一开启生产配额。
- 有试点需求时，由业务给出额度、单位、窗口及可容忍超额，再核对 Redis、租户上下文与批量调用需求，验证超额拒绝及计量故障行为。
- 交付说明明确“软阈值、非计费账本”；若需非空 batch 且用 tokens 配额，先处理 usage 合约缺口，不能假定其已支持。

**明确不做／延后：**不新增数据库用量账本，不给每租户开放 unit/window，不默认切换故障拒绝，不宣称严格费用封顶。

这里是认可现状的推荐，无需为本次报告重新向用户索要决定。政策文档仍有早期“无前端”等历史描述，最新 todo.md:22 已记管理前端落地，应按新记录理解，后续文档维护再同步。

## 5. 知识库选型：维持默认、优先级和投入方向

**推荐决策：认可既有代决：代码默认 provider 保持空，交付有条件时以 pgvector 起步；选择优先级保持 `pgvector 直配 → local → ragflow → dify → weknora`；新增增强投入集中 RAGFlow，维护 WeKnora，Dify 冻结新增能力，MaxKB 观察。**

来源：todo.md:26，`docs/design/knowledge-provider-selection-policy.md` §1—5。该顺序带各自启用与健康条件，不意味着一次请求一定逐个访问所有平台。本建议沿用仓内产品策略，不是对各平台当前市场能力的重新排名。

理由：

1. **成本：**不改选择链可减少回归与交付配置变动，把人力集中在真实验收上。
2. **收益：**代码默认空，保留无外部配置和 sqlite 部署形态；有 PostgreSQL 扩展及 embedding 条件的交付再显式配置 pgvector。
3. **风险：**直接把代码默认设成 pgvector，会让不具备这些前提的部署多出隐含依赖。
4. **兼容性：**Dify 排在 WeKnora 前是现有兼容策略，新增投入优先级与运行时选择顺序不是同一件事，无需为了看起来一致而改链。
5. **决策思路：**默认值决定所有新安装的后果，新增投入决定团队的未来成本；二者分别考虑，才能避免用一个“选哪家”问题绑住所有场景。

**立即执行动作（后续交办）：**

- 每个交付明确选择 provider 及其前提，不把代码默认空解释为已开箱启用知识库。
- 将新增测试资源优先用于第 2 项验收；有明确既有客户需求时调整验收顺序。
- 只在客户已有平台、解析需求或部署约束发生变化时重开选型，记录触发证据。

**明确不做／延后：**不改代码默认、不调整兼容顺序、不新增 MaxKB 接入、不扩展 Dify 新能力。冻结能力不等于停止修复兼容问题。

## 6. MetricsAggregator：保持单一对外读取出口

**推荐决策：认可已有代决，保留该聚合器经 `SnapshotSeries` 桥接到 Prometheus `/metrics`；维持旧有损 `Snapshot()` 退役。**

来源：todo.md:27；`apps/server/internal/handlers/metrics_ingest.go:64` 与 `metrics_prometheus.go`。本结论限于 MetricsAggregator，不推导成整个系统只能有一种观测手段。

理由：

1. **成本：**一个对外读取出口减少重复格式、权限和兼容维护，当前实现无需改动。
2. **收益：**`SnapshotSeries` 保留指标标签，让同名指标下的不同来源或结果能被区分。
3. **风险：**有损接口会丢失解释指标所需的维度；并存两个出口容易让用户看到互相难以对账的数字。
4. **边界：**运行指标适合监控，不自动成为跨实例可靠计费账本；若拿它算收费，应单独设计账务语义。

**立即执行动作（后续交办）：**运维验收时从 `/metrics` 抽查指标名、标签和数值是否满足现有看板需求；记录具体缺失项，仅在存在消费者需求时提出新读取能力。

**明确不做／延后：**不恢复旧 Snapshot，不再造同内容 JSON 读取 API，不以这份指标快照实现收费。这里没有新的外部输入阻塞。

理由：

1. **成本：**严格预算需要调用前原子预留、调用后结算、失败退款和崩溃恢复；不是调小一个额度就能获得。
2. **收益：**明确区分软保护和硬预算，避免交付承诺超过实现，也避免没有客户收益就先建设复杂账务系统。
3. **风险：**现有 token 记账在调用成功后发生，batch 缺 usage 合约，meter 故障放行，因此无法证明硬封顶。
4. **单位：**token 数量也不直接等于金额；若业务真正要求费用上限，还需模型价格、输入输出差异等计价规则。
5. **可逆性：**现在延期保留未来选择；一旦有明确客户和预算，再用可验证的“最坏超额是多少”驱动设计。

**立即执行动作（后续交办）：**

- 交付统一使用“软配额保护”的措辞，不作硬费用保证。
- 出现立项触发时，产品先给出计量对象（次数／token／金额）、允许超额量、计量服务故障时能否中断翻译、并发规模和预算归属。
- 工程再依次补 batch usage 合约、设计预留／结算与故障处理，估算成本并给出可验收边界。该阶段完成前不对外承诺日期或封顶金额。

**明确不做／延后：**本期不建计费账本、不默认故障拒绝、不把软配额改名为硬预算；没有商业触发时不启动实现。
